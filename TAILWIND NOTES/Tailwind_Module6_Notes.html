1Pseudo-Class Variants

A variant is a prefix that makes a utility class apply only under a specific condition instead of always. Pseudo-class variants apply based on interaction state, matching CSS pseudo-classes like :hover and :focus.

VariantApplies when
hover:The pointer is over the element
focus:The element has keyboard or click focus
active:The element is being actively clicked or pressed
disabled:The element has the disabled attribute (form elements)
focus-visible:Focused specifically via keyboard navigation, not a mouse click
<button class="bg-violet-600 hover:bg-violet-500 active:bg-violet-800 text-white px-5 py-3 rounded-lg">
  Save changes
</button>

Each variant only overrides the property it sets. In the example above, three different shades of the same color are defined for three different states, and the browser switches between them automatically, no JavaScript involved.

Focus on form fields

<input class="border border-slate-600 focus:border-sky-500 focus:ring-2 focus:ring-sky-500/40 rounded-lg px-4 py-2">

ring-* adds a glow-style outline around an element, commonly paired with focus: to give clear visual feedback that a field is active, without changing the element's layout size the way a thick border would.

2Group Variants

Group variants style a child element based on the state of its parent. The parent is marked with the group class, and the child uses group-hover:, group-focus:, or similar, to react to the parent's state.

<div class="group bg-slate-800 rounded-lg p-4 cursor-pointer hover:bg-slate-700">
  <p class="text-slate-400 group-hover:text-sky-400 group-hover:underline">
    Read more
  </p>
</div>

Hover this whole card, watch the text below react

Why this exists: without group, hovering a child only affects that child's own hover state. group lets an entire card, row, or link area trigger style changes on elements nested inside it, without needing separate hover listeners on every child.

3Peer Variants

Peer variants style an element based on the state of a sibling element, not a parent. The sibling being watched is marked with the peer class, and the element reacting to it uses peer-hover:, peer-focus:, peer-checked:, or similar.

<input type="checkbox" class="peer">
<p class="text-slate-500 peer-checked:text-emerald-400">
  Turns green once the checkbox above is checked
</p>
Important ordering rule: the peer element must come before the element reacting to it in the HTML. This only works on later siblings, not earlier ones, because of how the underlying CSS selector is built. If the reacting element is placed before the peer in the markup, the effect will not work.

Common use case: floating label inputs

A very common real-world pattern: an input marked as peer, with a label that changes position or color using peer-focus:, entirely in CSS with no JavaScript.

4Dark Mode

The dark: variant applies a utility only when dark mode is active. By default, this follows the operating system or browser's color scheme preference automatically, no configuration required.

<div class="bg-white text-slate-900 dark:bg-slate-900 dark:text-white p-6 rounded-lg">
  Adapts automatically to system dark mode
</div>
Key point: dark: classes only define what changes in dark mode. The light-mode styles still need to be written as normal, unprefixed classes on the same element. There is no single class that means "dark mode base style," both states are declared side by side.

A project can be switched from automatically following the system preference to a manually toggled dark mode (such as a button the user clicks), but that requires a small config change in the build setup. This course uses the automatic, system-based version by default.

5Transitions & Basic Animation

Without a transition class, state changes (like a hover color swap) happen instantly, in a single frame. transition-* classes make that change animate smoothly instead.

ClassEffect
transitionEnables smooth animation for common properties (color, background, border, opacity, shadow, transform)
transition-colorsAnimates only color-related properties, more efficient if that's all that's changing
duration-300Sets how long the transition takes, in milliseconds
ease-in-outControls the acceleration curve of the animation
<button class="bg-sky-600 hover:bg-sky-500 transition-colors duration-300">
  Smooth hover
</button>
Common mistake: adding hover: color changes without a transition class produces an abrupt, instant color swap. The transition class must be added separately, it is not automatic just because a hover variant exists.

6Stacking Variants

Variants can be combined by writing them one after another before the utility, applying the utility only when every condition in the chain is true at once.

<button class="dark:hover:bg-fuchsia-600">
  Only fuchsia when in dark mode AND hovered
</button>

<button class="disabled:hover:bg-sky-500">
  Keeps the same background on hover, even while disabled
</button>
Order matters when combining responsive size, dark mode, and state: the correct order is responsive breakpoint first, then dark:, then the interaction state, e.g. md:dark:hover:bg-slate-700. Writing them in a different order can fail to apply correctly.

?Common Questions & Misconceptions

Mythgroup-hover: and hover: do the same thing.
hover: reacts to the element's own hover state. group-hover: reacts to a parent element's hover state, and requires that parent to carry the group class. Applying hover: directly to a child only affects that child when the mouse is over the child itself, not the surrounding card.
Q&AWhy doesn't my peer-checked: style apply?
The most common cause is ordering: the peer element must appear before the reacting element in the HTML. If the label or text meant to react comes before the input carrying the peer class, it will not work, since the underlying selector only looks at later siblings.
MythAdding hover: automatically makes the color change smooth.
Incorrect. Without a transition class, the change is instant. transition (or a more specific variant like transition-colors) must be added explicitly for the change to animate.
Q&ADo I need to write a separate class for dark mode's base style?
No such thing exists. Light mode styles are written as normal, unprefixed classes. dark: classes only specify what changes when dark mode is active, both sets sit side by side on the same element.
MythVariants can be stacked in any order.
Order matters for correct behavior. The convention is responsive breakpoint first, then dark mode, then interaction state, for example md:dark:hover:bg-slate-700. Writing it out of order can cause the utility to not apply as expected.
Q&AWhat's the difference between focus: and focus-visible:?
focus: applies whenever the element has focus, including a plain mouse click. focus-visible: applies more narrowly, generally only when focus was reached through keyboard navigation, which avoids showing a focus ring after every mouse click while still preserving it for keyboard users.

✓Summary

  • Pseudo-class variants (hover:, focus:, active:, disabled:) apply a utility only during that interaction state.
  • group on a parent plus group-hover: (or similar) on a child lets the child react to the parent's state.
  • peer on a sibling plus peer-* on a later sibling lets one element react to another, order in the HTML matters.
  • dark: applies a utility only in dark mode, following the system preference by default. Light-mode styles are still written normally alongside it.
  • transition-* and duration-* must be added explicitly for state changes to animate smoothly, this is not automatic.
  • Variants stack in order: responsive breakpoint, then dark mode, then interaction state.
